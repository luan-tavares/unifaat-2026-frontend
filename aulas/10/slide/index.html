P = pausa · ↑ ↓ = passo
  1. Passo 1. O cliente faz a requisição e fica esperando a resposta: cada segundo gasto no servidor é um segundo de loading.
  2. Passo 2. O controller faz só o necessário: valida e grava no banco.
  3. Passo 3. O dispatch() só deixa um recado na fila (leva milissegundos) e o controller já responde 201.
  4. Passo 4. O worker, em outro container, pega o recado e faz o trabalho pesado depois, fora do ciclo HTTP.

P = pausa · ↑ ↓ = passo
  1. Passo 1. Os producers ficam fora do RabbitMQ (controller HTTP, comando ou outro worker) e só sabem lançar a mensagem.
  2. Passo 2. A mensagem entra pela entrada do RabbitMQ: uma conexão TCP na porta 5672, com um canal AMQP.
  3. Passo 3. Dentro da caixa, toda mensagem passa por um exchange. Aqui é o exchange padrão (""), que roteia pelo nome da fila.
  4. Passo 4. Os bindings ligam o exchange às filas: a routing key (igual ao nome da fila) decide o destino.
  5. Passo 5. A fila guarda a mensagem (é durável) até alguém consumir. O producer não espera ninguém.
  6. Passo 6. Os workers ficam fora da caixa, pendurados na fila. O RabbitMQ empurra cada job para um só deles: um pool em revezamento.
  7. Passo 7. Filas diferentes, workers diferentes. Escalar jobs = pendurar mais workers na mesma fila.

P = pausa · ↑ ↓ = passo
  1. Passo 1. O controller (producer) só chama Job.dispatch("default", payload). Ele não sabe como o trabalho é feito.
  2. Passo 2. Na fila viaja só uma mensagem JSON: o nome do job e o payload (por exemplo, só o id), nunca funções.
  3. Passo 3. O _worker.js carrega todos os jobs de app/Jobs e procura o nome da mensagem.
  4. Passo 4. O job é a unidade de execução: handle(payload) descreve o que fazer.
  5. Passo 5. A regra de negócio mora no service, que qualquer controller ou comando pode chamar: uma responsabilidade por camada.

Por isso o payload leva só o id: o service lê o estado atual no Postgres na hora de executar.

Um job, um worker: ack e idempotência

producerdispatch
filadefault
worker 1recebeu o job
worker 2não recebeu (a fila é de um só)
ack"terminei": só agora a fila apaga
✕
☠ morreu depois de executar, antes do ack
worker 2recebe de novo e executa
idempotente?executar 2x = executar 1x. O Elastic sim; "cobrar a fatura" não
P = pausa · ↑ ↓ = passo
  1. Passo 1. O producer lança um job e ele fica na fila.
  2. Passo 2. O RabbitMQ entrega o job a um único worker da fila. O outro não recebe: cada mensagem é de um só.
  3. Passo 3. A mensagem só sai da fila quando o worker manda o ack (confirmação), depois do handle.
  4. Passo 4. E se o worker morre depois de executar e antes do ack? A fila acha que ninguém processou.
  5. Passo 5. O job é entregue de novo a outro worker. A garantia é pelo menos uma vez: o job precisa ser idempotente.

Entrega a um só é propriedade da fila. Idempotência é propriedade do job.

P = pausa · ↑ ↓ = passo
  1. Passo 1. Os dois lados começam igual: um producer lança uma mensagem. A diferença está no que acontece depois.
  2. Passo 2. Fila: o job 1 vai para um worker. Fanout: a mesma mensagem é copiada para a fila de cada consumidor.

Configurando o exchange na conexão

await ch.assertExchange("notifications", "fanout")
// cria o exchange (se já existe, tudo bem)

const { queue } = await ch.assertQueue("", { exclusive: true })
// fila SÓ deste processo; some ao desconectar

await ch.bindQueue(queue, "notifications", "")
// binding: o fanout ignora a routing key

await ch.consume(queue, onMessage)
// producer: ch.publish("notifications", "", msg)
exchangenotificationsfanout
filac1exclusiva, nome gerado
bindQueue
consumerconsume(fila)
P = pausa · ↑ ↓ = passo
  1. Passo 1. O exchange é declarado no canal da conexão com assertExchange: nome e tipo.
  2. Passo 2. Cada consumidor cria a própria fila dinâmica (exclusive, sem nome): uma fila por consumidor, no mesmo exchange.
  3. Passo 3. O binding liga a fila ao exchange. A partir daqui toda mensagem publicada no exchange é copiada para ela.
  4. Passo 4. O consumidor consome a sua fila. O producer publica no exchange e não sabe quantos consumidores existem.

P = pausa · ↑ ↓ = passo
  1. Passo 1. No HTTP o cliente sempre vai atrás do servidor: pergunta, recebe a resposta e a conexão acaba. O servidor nunca fala primeiro.
  2. Passo 2. A saída antiga é o polling: perguntar toda hora "tem novidade?". Gasta requisição à toa e ainda atrasa.
  3. Passo 3. No WebSocket quem inicia é o cliente (por isso funciona atrás de NAT e firewall): abre o túnel uma vez.
  4. Passo 4. Com o túnel aberto a troca é bidirecional: o servidor empurra e o cliente envia, sem novo pedido.

  1. Passo 1. O navegador já traz a API WebSocket, mas o servidor Node precisa de uma biblioteca (ws): uma em cada ponta.
  2. Passo 2. O Socket.IO traz as duas pontas (socket.io e socket.io-client) com eventos nomeados, reconexão e salas. É a nossa escolha.

O Socket.IO começa por long polling e sobe para WebSocket: no Network você vê o polling e depois a linha 101.

P = pausa · ↑ ↓ = passo
  1. Passo 1. O aluno envia uma imagem. O websocket não processa: Node tem um fio só, e uma conta pesada aqui congelaria todos os túneis.
  2. Passo 2. O Event só faz o dispatch de um job na fila images e responde na hora. O websocket segue livre.
  3. Passo 3. Um worker (outro container, no mesmo RabbitMQ) pega o job: redimensionar e gerar a miniatura roda aqui.
  4. Passo 4. Terminou: o worker publica o resultado em outro exchange, o results.
  5. Passo 5. Cada websocket cria a sua fila dinâmica nesse exchange: o fanout copia o resultado para a fila de cada um.
  6. Passo 6. Cada websocket faz io.emit pelos túneis dos seus clients: todos veem a imagem, e o chat nunca parou.

Websocket e worker são containers diferentes no mesmo RabbitMQ: o websocket cuida das conexões, o worker cuida da conta.

P = pausa · ↑ ↓ = passo
  1. Passo 1. Parecidos: dois entrypoints Node que se penduram no mesmo RabbitMQ, cada um com a sua unidade (Job e Event).
  2. Passo 2. Websocket → worker: o Event lança um job na fila e o worker consome. É o websocket pedindo o trabalho pesado.
  3. Passo 3. Worker → websocket → client: o worker lança um evento no exchange e o websocket entrega ao client pelo túnel.
  4. Passo 4. O worker não é servidor: sem porta, só a conexão do RabbitMQ. Ninguém bate nele, e ele pode ser pesado.
  5. Passo 5. O websocket é servidor: porta 3001 e os túneis dos clients, entre o RabbitMQ e o client. Por isso nada pesado nele.

O worker faz o pesado; o websocket segura as conexões. Os dois compartilham um fluxo só, nos dois sentidos.

P = pausa · ↑ ↓ = passo
  1. Passo 1. Os 10 alunos abrem túneis. A porta de entrada é uma só: o nginx, que recebe todos.
  2. Passo 2. O nginx distribui as conexões entre as réplicas (upstream): 4, 3 e 3. Cada túnel fica preso à réplica escolhida.
  3. Passo 3. Cada réplica tem a sua fila dinâmica no exchange: a mensagem de um client chega a todas, e cada uma entrega aos seus.
  4. Passo 4. O nginx também entra na escalabilidade: mais réplicas (--scale) e o nginx repartindo. O exchange cuida do resto.

Mais websockets só ajudam se o nginx reparte os túneis entre eles; o exchange garante que a mensagem chegue a todos.
